# 团队协作框架

三人团队的协作约定。目标是**让三个人各有一条能独立演示的完整链路**，而不是把技术层拆开各管一段。

## 一、角色与职责

| 角色 | 负责主线 | 主责文件 | 答辩负责模块 |
| --- | --- | --- | --- |
| **A 数据与治理** | 接入 + 清洗 + 校验 | `ingest.py`、`cleaning.py`、`config/schema.json`、`config/cleaning_rules.json`、`data/reference/` | 数据接入与清洗 |
| **B 分析与可视化** | 多维分析 + 图表 | `analytics.py`、`charts.py`、`geo.py`、`plans.py`、`config/chart_rules.json` | 多维多层级分析、可视化图表 |
| **C 报告与智能体** | 报告 + 问答 + 界面 | `report.py`、`agent/`、`config/report_outline.json`、`web/` | 报告生成、智能问答 |

划分依据是赛项四个模块与它们的输入输出边界。每个人手里都是一条端到端链路，答辩时各讲各的，被追问也能接住。

## 二、文件所有权

### 独占（谁主责谁改）

见上表。改自己主责的文件不需要任何人同意。

### 共享（改动前必须在群里说一声）

| 文件 | 为什么敏感 |
| --- | --- |
| `disaster_agent/models.py` | 模块间的数据契约，改字段名会同时影响三个模块 |
| `disaster_agent/pipeline.py` | 流程编排，改阶段顺序会影响所有人的调试 |
| `config/schema.json` | 字段、指标、维度的总定义，B 和 C 都依赖它 |
| `README.md` / `CHANGELOG.md` | 多人同时改必然冲突 |

**规则**：要动共享文件，先在群里发一句话说明改什么、影响谁，另外两人确认后再动手。这不是流程繁琐，这是三人项目唯一能避免合并地狱的办法。

## 三、接口冻结

模块之间只通过 `models.py` 里的几个数据结构通信。**开工前先把这几个结构确认一遍**，之后任何改动都走三步：

1. 提出：说明为什么要改、改哪个字段
2. 确认：另外两人确认自己的模块是否受影响
3. 同步：一次性改完所有调用方，不留半成品

涉及的数据结构：

- `IngestReport` —— 字段比对报告
- `CleaningLog` / `CleanStep` —— 清洗审计日志
- `AnalysisRequest` / `AnalysisResult` —— 分析计划与结果
- `ChartSpec` —— 图表规格（静态图路径 + 前端配置）

## 四、分支模型

| 分支 | 用途 | 谁能推 |
| --- | --- | --- |
| `main` | 稳定分支，用于发版 | 只接受合并，不直接提交 |
| `develop` | 集成分支，日常基线 | 三人都可合并 |
| `feature/*` | 个人开发分支 | 各自维护 |

```bash
# 开工
git switch develop && git pull
git switch -c feature/data-quality      # A
git switch -c feature/analytics         # B
git switch -c feature/report-agent      # C

# 收工
python tests/test_pipeline.py           # 必须 9 项全过
git add -A && git commit -m "清洗：新增勾稽校验"
git push -u origin feature/data-quality
```

**合并顺序：A → B → C。** 下游依赖上游的数据结构，反序合并会把冲突堆到最后一个人身上。

**提交信息格式**：`模块：做了什么`

- `清洗：补充绝收面积与受灾面积的勾稽校验`
- `图表：解决县名重名导致的着色串色`
- `文档：更新使用说明的启动步骤`

## 五、交付标准

一个任务算"完成"，必须同时满足五条：

1. `python tests/test_pipeline.py` **9 项全过**
2. 相关文档与配置同步更新（改了规则就更新 `config/`，改了用法就更新 `使用说明.md`）
3. 涉及界面或图表的改动，**附截图**发到群里
4. 在 `CHANGELOG.md` 记一条
5. 已合并到 `develop` 并推送

少任何一条都不算完成。特别是第 3 条——"我这边好了"和"别人看到的是对的"经常是两回事。

## 六、同步机制

**每日三句话**（发群里，不用开会）：

1. 昨天做完了什么
2. 今天打算做什么
3. 卡在哪里

三人项目卡住往往不是技术问题，是"我以为你会做"。

**每周一次 30 分钟评审**：跑一遍全流程，对着赛项要求逐条自查（清单见 `项目计划.md` 第七节）。

**演示前 3 天起**：每天完整走一遍演示脚本。不做这一步，现场大概率出问题。

## 七、答辩分工

| 角色 | 职责 | 注意 |
| --- | --- | --- |
| 主讲 | 讲背景、架构、价值，控制节奏 | **不要一边讲一边操作电脑** |
| 操作 | 按脚本点操作，管好演示机 | 脚本写死到"第几步点哪个按钮" |
| 答疑 | 谁负责的模块评委问谁答 | 不抢答，主讲负责衔接 |

必备的应急方案：

- 提前录一份完整演示视频，现场环境出问题直接放
- 准备离线模式说辞：没有网络时自动用规则模型，功能不缩水
- 记住三个数字：**476 条记录、26 项清洗动作、10 张图表**，被问到规模时张口就来

## 八、常用命令

| 场景 | 命令 |
| --- | --- |
| 启动平台 | 双击 `启动.bat`（或桌面快捷方式） |
| 停止平台 | 双击 `停止.bat` |
| 环境自检 | 双击 `自检.bat`，或 `python tests/test_pipeline.py` |
| 命令行跑通 | `python -m disaster_agent.cli run --agent` |
| 自然语言问答 | `python -m disaster_agent.cli ask "近五年洪涝灾害直接经济损失趋势"` |
| 查看维度与指标 | `python -m disaster_agent.cli catalog` |
| 检查大模型配置 | `python -m disaster_agent.cli llm-check` |
| 打分发版 | 双击 `打包Beta.bat` |
